# Blind Spots 03 — Engineering / Technical Architecture Gaps

*Research subagent report · 2026-11-17 · Sources: `PLAN.md`, `USE-CASES-EXPANSION-V2.md`, plus current primary sources listed in §5.*

---

## 1. Executive summary

Both source docs are unusually strong on *what* the harness does and *why* (safety tiers, memory tiers, use-case economics, competitive intel). They are markedly thinner on *how it is engineered as a long-lived distributed system on a user's machine*. I verified 15 concrete gaps by grep + targeted section reads (§2, §3, §5, §7, §11, §13, §19, Appendices of PLAN.md; §2, §3, §5 of USE-CASES-EXPANSION-V2.md) and checked each against current primary standards.

The unifying pattern is: **the docs name standards and patterns but do not specify lifecycles, schemas, or operational contracts.** AID v2.1.1 / JWS / RFC 9421 are named (PLAN §23.4, §31) with no key lifecycle; event sourcing is named as a T3 blueprint (§19) and committed to the repo layout (Appendix A) with no projection/snapshot/outbox semantics; "full session replay/observability" is a differentiator (§20) with no telemetry schema or trace-context propagation; a "single signed binary" is in §11 with no update framework, provenance attestation, or verification path. Several entire engineering concerns are absent from both docs: i18n, accessibility of the harness's *own* UI, schema migrations, protocol versioning, latency budgets, long-run memory management, and resource-constrained operation.

Highest priority (P1): (1) an OpenTelemetry GenAI instrumentation + distributed-trace design, (2) a real PKI/key-lifecycle for AID/JWS/RFC 9421, (3) secure auto-update and supply-chain provenance (TUF + SLSA + Sigstore). These are not gold-plating: the docs' own threat model (§24), identity posture (§23.4), and distribution plan (§11, 80–120 MB signed binary, per-user install) all depend on them, and 2026 primary sources show the standards have moved enough that designing without them now guarantees rework.

## 4. Top 5 in depth

### 4.1 Observability schema + trace propagation (gap #1)

**What exists today:** `correlationId` in every tool result (§5), a hash-chained audit log (§2/§6), and "full session replay/observability" as a marketed differentiator (§20). That is *event logging*, not distributed tracing or a GenAI telemetry schema.

**Why the 2026 landscape forces a design now:** The GenAI semantic conventions moved to `open-telemetry/semantic-conventions-genai` in v1.42.0 (June 2026); as of early Nov 2026 every GenAI signal is marked **Development**, there is no tagged release, and the agent-span guidance changed again in v1.41.0/PR #524 (invoke_agent client vs internal). Real frameworks have already broken dashboards on a version bump (LiveKit Agents 1.8.0 mapped `gen_ai.system.message` event → `gen_ai.system_instructions` attribute). "We emit OTel" is therefore not a stable contract.

**Design:**
- Internal telemetry model owned by us, pinned; an `OTLPExporter` adapter maps it to a pinned semconv commit. Keep dashboards on internal names.
- Spans: `invoke_agent.internal` (in-process loop; `client` only for remote subagent services), `plan`, `chat` (per model call), `execute_tool`, `retrieval`, `memory`. Nest subagents and background jobs under the parent `invoke_agent` via W3C `traceparent` carried in the JSON-RPC envelope (reuse `correlationId` as the span-link carrier).
- Attributes: `gen_ai.operation.name`, `provider.name`, `request.model`, `response.model`, `usage.input_tokens/output_tokens/cache_read.input_tokens` (include cached tokens in input, reasoning in output — do not double count), `conversation.id`, `error.type`. **Content opt-in and off by default** (§6.6 redaction), with a retention policy if enabled.
- Metrics: internal `harness.step.duration`, `harness.tool.duration`, `harness.cost.usd`, `harness.retry.count`; evaluation events for the §13 task suite.
- Privacy: telemetry off by default, opt-in, aggregate-only already stated in §6.6 — keep wire-verifiable (§27 #1); emit traces to a local file/OTLP collector the user controls, never a vendor endpoint by default.

### 4.2 Key lifecycle for AID / JWS / RFC 9421 (gap #2)

The doc commits to emitting AID records and RFC 9421 headers (§23.4), a JWS/RFC 8785 signed Agent Card (§27), and detached JWS claim manifests (§31) — but never says where the private key lives or what happens when it is lost.

Current primary sources make the required specifics concrete:
- **RFC 9421** (Feb 2024) defines the signature base, `Signature`/`Signature-Input`, and parameters `created`, `expires`, `nonce`, `keyid`, `alg`, `tag`. Registered algs include `ed25519`. Body is covered only via `content-digest` (RFC 9530).
- **Web Bot Auth**: WG draft `draft-ietf-webbotauth-httpsig-protocol-01` (Oct 2026). Must cover `@authority` or `@target-uri`; must send `created`, `expires`, `keyid` = base64url JWK SHA-256 thumbprint, `tag="web-bot-auth"`; lookup keyed on **(URL, key)**; expiry recommended ≤24h; **rotation by publishing old+new then dropping old**; **no revocation** — cached-directory expiry is the only bound (negatives ≤5 min). Cloudflare's shipped verifier is Ed25519-only and follows an older directory dialect; OpenAI's live directory has extra fields. Implement to the WG draft with a compatibility switch for deployed dialects.
- **Cryptoperiods** (OWASP KMS cheat sheet / NIST SP 800-57): digital-signature private keys 1–3 years; log all state transitions (pre-activation → active → deactivated → compromised → destroyed); a compromised recovered key must be revoked and replaced.

**Design addition:** a `KEY-MANAGEMENT.md` with key records `{kid, alg, purpose, created, activated, expires, state, storage_ref}`, DPAPI/TPM custody, JWKS served at the well-known path, overlap rotation, a revocation list in AID DNS TXT plus short `Cache-Control` (compensating for the protocol's revocation gap), one key per agent (never shared HMAC), and a reserved PQ/hybrid slot.

### 4.3 Secure auto-update + supply-chain provenance (gap #3)

The distribution plan (§11) promises a signed single binary and per-user auto-start, but §11–§12 contain no updater design, and §24/§15 identify supply-chain RCE as *the* top threat. The 2026 toolchain makes a concrete, affordable design possible:

- **TUF v1.0.37** (Oct 2026): four roles — offline Root (threshold ≥2, roots shipped with client), offline Targets, offline Snapshot, online Timestamp. Version numbers defeat rollback, expirations defeat freeze, Snapshot defeats mix-and-match, thresholds defeat single-key compromise. Update workflow: fixed start time → root chain → timestamp → snapshot → targets → target with byte caps and hash checks. Offline root rotation by chaining requires signatures from old and new keys — exactly the long-lived-install case here.
- **Sigstore keyless**: Fulcio 10-minute cert bound to OIDC identity + cosign + Rekor transparency log removes the long-lived release private key (which otherwise needs the lifecycle from #2). Verification pins `--certificate-oidc-issuer` and `--certificate-identity-regexp`.
- **SLSA v1.2**: Build L2 from hosted provenance (`slsa.dev/provenance/v1` in-toto predicate); L3 needs an isolated reusable build workflow keeping signing material out of build steps. Add an SPDX/CycloneDX SBOM (SLSA provenance and SBOM answer different questions — transparency vs integrity vs provenance).

**Design addition:** release pipeline emits binary + TUF metadata + cosign bundle + SLSA provenance + SBOM; updater verifies before applying; an "verify this install" command and a signed **offline update bundle** (#13) reuse the same Root/Targets keys. Keep release keys, AID signing keys, and DPAPI session encryption keys in separate key records.

### 4.4 Durability contract for the event store (gaps #4 + #5)

§19 correctly identifies T3's `EventSink` (events + projections + outbox in one SQLite transaction), `EffectWorker`, and `CommandReceiptStore` as best-in-class, and Appendix A allocates `runners/orchestrations/`. But no schema, ordering rule, rebuild procedure, or migration strategy is written. Concretely:

- One SQLite DB with `events`, `projections/<name>`, `outbox`, `command_receipts`, `snapshots`, `schema_migrations`; single writer guard + WAL (§11).
- `command_id` unique index makes retries idempotent (mirrors §3.1 idempotency keys); `correlation_id` links to OTel (#1).
- Projection rebuild is a first-class command with a checksum test; snapshot every N events; dead-letter + replay for poison events.
- Forward-only migrations with expand→contract and fixtures from the last three releases; backup before destructive `ALTER` (SQLite's limited `ALTER TABLE` makes this non-optional).

### 4.5 Testing the invariants, not just the examples (gap #8)

§13 is a solid *example-based* suite; the 2026 literature converging on agent testing says the missing layer is **properties + replay**:

- Chronicle (Microsoft, 2026): records nondeterministic boundaries as immutable envelopes; **cut-point replay** serves selected boundaries from the record and executes the rest live, turning a 3 a.m. incident into a CI regression test. Full replay = 0 model calls, bit-stable across 20 repetitions; cut-point tests caught every unsafe-action mutant where stub-everything caught none.
- Property-based testing (Anthropic 2026 found real bugs in NumPy/SciPy/Pandas with an agent-generated PBT approach; Orloj 2026 gives the agent invariant set): authorization, idempotency, isolation, governance fail-closed — assert what the *system* prevents, independent of model choice.
- Deterministic simulation testing (Antithesis): control clocks, thread interleaving, randomness; pair with fault injection and PBT — a direct fit for the event store/actors in #4/#7.
- Fuzzing: agent-synthesized structured generators (Gentoo, 2026) beat human baselines on branch coverage — apply to the §6.1 canonicalizer and §5 envelope parser.

**Design addition:** extend `evals/` with a property suite, a journaled record/replay harness with cut-point tests in CI, a seeded deterministic simulator for the event store, and a nightly live-eval budget with cached responses (#15). This is the highest-leverage way to make the "long-horizon reliability" bet (§22) measurable.
