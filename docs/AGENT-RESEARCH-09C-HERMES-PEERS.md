## 3. Where Hermes is genuinely ahead — and adoption mapping to `Optimal/phases.md`

"Genuinely ahead" = a mechanism that is **more complete, more reviewable, or shifts the default in our favour**, not merely a different trade-off. Each item states why it beats *both* peers where possible.

### A. Execution-location portability (ahead of OpenClaw and MantisClaw)
**Mechanism:** terminal backend is a first-class setting — `local | Docker | SSH | Singularity | Modal | Daytona | Vercel Sandbox` (plus OpenShell whole-process wrapping); serverless backends hibernate when idle; "talk to it from Telegram while it works on a cloud VM". OpenClaw's sandbox is a per-agent setting that is **off by default**; MantisClaw is host-only. ✅
**Why genuinely ahead:** it makes *blast-radius selection* an operator decision at task granularity rather than a gap you fill later. Our O1.5 already says "unenforceable policy is refused, not downgraded" — Hermes' backend abstraction gives us a concrete taxonomy of enforceable targets.
**Maps to:** **O1.5** (Windows boundary / capability SIDs — adopt the backend taxonomy, keep MXC as the strongest rung), **O5.2** (input ladder — same "lowest sufficient rung" discipline applied to execution), **O7.3** (offline profile — choose local backend explicitly), **O6.3** (background jobs surviving window close — serverless/remote backend reference).

### B. Whole-process sandbox with *inference-routing* policy (ahead of OpenClaw's tool sandbox)
**Mechanism:** NVIDIA **OpenShell** integration gives per-session sandboxes with declarative policy across **filesystem, network (L7 egress), process/syscall, and inference-routing**, with **hot-reloadable** network/inference policy and credentials injected from a Provider store that never touch sandbox filesystem. Hermes' own SECURITY.md names whole-process wrapping as the supported posture for untrusted input; `NVIDIA/NemoClaw` (23,048★) wraps both Hermes and OpenClaw this way. ✅
**Why genuinely ahead:** our plan's egress DLP (O1.4) is a build-time allowlist + receipt; Hermes/OpenShell adds *L7 egress + inference-routing* as the same declarative policy object and hot reload — genuinely more complete than a static allowlist. **Inference-routing policy is the piece our O4.3/O8.4 model matrix currently lacks.**
**Maps to:** **O1.4** (add L7 egress + hot-reloadable policy + "what left the machine" receipt), **O1.5** (capability isolation), **O4.3** (pin model/inference endpoint as part of policy), **O8.4** (no silent model swap — inference-routing policy is the enforcement layer).

### C. Reviewable self-improvement loop (ahead of OpenClaw's Skill Workshop defaults)
**Mechanism:** skill writes are staged (`skills.write_approval: true` → `~/.hermes/pending/skills/`, `/skills diff`, approve/reject), **locked skills** refuse all programmatic write paths, advisory linter warns on incident-log shape / reference sprawl / oversized body, progressive disclosure keeps the fixed system prompt cacheable, and a locked changelog-stamped provenance `lock.json`. OpenClaw's analogous self-learning defaults to `auto`; MantisClaw's self-healing skills have no documented gate. ✅
**Why genuinely ahead:** it is the only implementation in this comparison where "the agent writes its own procedures" is paired with a **diff-based human gate and a per-skill lock**, which is exactly the shape our `BEST-OF-ADOPTION.md` §3 #5/#10 wants (mandatory declarations + hash-trusted changes). **Invert the default:** Hermes ships `write_approval: false`; ours must default to review-required.
**Maps to:** **O3.2** (diff cards with accept/reject — `/skills diff` is a ready-made UX pattern), **O4.4** (vetted install, scoped revision, auto-disable, managed-only channel — adopt lock + quarantine + trust levels, invert the default), **O2.4** (file-first memory with re-validation), **O6.2** (guardian advisory — never let the model edit its own gate).

### D. Bounded, frozen memory injection (ahead of OpenClaw on poisoning surface — *architectural*, not empirically proven)
**Mechanism:** two small files with hard char caps injected once at session start and **frozen**; recall via FTS5 over full session history with LLM summaries; `memory.write_approval` gate. OpenClaw injects up to 60,000 chars of workspace Markdown every session. ✅
**Why ahead:** `PLAN.md` §23.3 / §26 note memory poisoning raising ASR 24.6%→74% (arXiv:2604.04759) and graph-memory 93.8%; a smaller, frozen injection surface mechanically reduces what a poisoned file can do in a single turn. ⚠️ **This is an architectural argument, not a measured result** — flagged as hypothesis below. Our O2.4 is still stricter because it re-validates stale facts against current files.
**Maps to:** **O2.4** (file-first memory + TTL/staleness — adopt the caps-and-frozen pattern, add our re-validation), **O0.5 / O4.7** (TTSR + audit — Hermes' scanner CVEs show in-process scanning is not a boundary).

### E. Skills Hub supply-chain vetting (ahead on mechanism; note the shared ClawHub exposure)
**Mechanism:** multi-source hub (official, skills.sh, ClawHub, LobeHub, browse.sh, direct URL/GitHub taps, NVIDIA signed skills) with **security scan on every install**, content-hash + scanner-version + source recorded in `lock.json`, `dangerous` verdict **cannot be overridden by `--force`**, scan-time quarantine of project skills on every content change, hash-cached outside the repo, and an optional **advisory** NVIDIA SkillEvaluator second opinion. ✅
**Why ahead of ClawHub's "trust envelope" alone:** the quarantine + immutable `dangerous` verdict + re-scan-on-content-change is a stronger install-time contract. But **CVE-2026-82021** (critical, mutable-branch MCP catalog) shows their *first-party catalog* violated its own pinning rule — so copy the mechanism, **not** the trust level, and keep our fail-closed O4.6 OSV gate.
**Maps to:** **O4.4** (skills/plugins), **O4.3** (server pinning + description scanning), **O4.6** (OSV fail-closed — apply to catalog *sources* too, not just packages), **O8.2** (external contributor pipeline).

### F. Managed one-click local inference (ahead of both peers on offline UX)
**Mechanism:** Hermes downloads a pinned, SHA-256-verified llama.cpp build matched to the machine, rates every catalog model against GPU/RAM, picks the highest-quality build that fits (never below 4-bit), guarantees ≥64K context and ≥20 tok/s recommendation floor, spills in least-harmful order (expert weights first, never attention cache), grows context with `Context window grown` status, compresses rather than over-claiming a window, unloads idle models after 15 min. ✅
**Why ahead:** OpenClaw requires you to manage Ollama yourself and warns the OpenAI-compatible path breaks tool calls; MantisClaw has no documented offline model story. Hermes is the closest thing in this class to our **O7.3** done correctly — except it publishes **no zero-outbound proof**, which we add.
**Maps to:** **O7.3** (offline/air-gapped profile — copy the runtime-sizing and verification design; add trace-proven zero outbound), **O7.4** (resource envelope — idle unload + placement policy), **O8.4** (published model matrix — their per-hardware model rating is a good UX pattern).

### G. Migration path as a trust-lowering mechanism (unique)
**Mechanism:** `hermes claw migrate --dry-run` imports an OpenClaw persona, memories, user-created skills, command allowlist, messaging settings and selected API keys; no reverse path exists. ✅
**Why genuinely ahead:** reduces switching cost *without* requiring us to compromise on our safety spine — a strategically useful pattern for O8 productization.
**Maps to:** **O8.3 / O8.4** (export/import + "why did you do that" export; we should ship a clean importer so users can bring skills/memories into our governed pipeline) and **O8.2** (licensing/governance clarity).

### H. Honest, load-bearing trust-model documentation (ahead as an *organizational* mechanism)
**Mechanism:** SECURITY.md names exactly one boundary (OS), enumerates two isolation postures, declares every in-process control a heuristic, scopes out prompt-injection-per-seen, says "profiles are not tenants", has a 90-day coordinated disclosure window, and publishes a 13-step hardening checklist. ✅
**Why ahead:** peers document features; Hermes documents *what its controls do not do*. That is the exact posture our `BEST-OF-ADOPTION.md` §1 "most important refusal" demands.
**Maps to:** **O0.4 / O1.5** (our `never` default + Z3 validation + OS boundary), **O7.5** (honest eval disclosure — no borrowed numbers), **O8.4** (changelog + wire-verifiable telemetry opt-out), and the cross-cutting rule "guardian is advisory, OS is boundary".

### I. Interop signals worth watching, not yet adopt-now
A2A v1.0 bundled plugin, HMAC-signed outbound lifecycle webhooks, MCP client **and** MCP-server mode, Bot Mode `hermes peer` agent-to-agent DMs, `/goal` cross-turn focus, trajectory export/compression for RL training, cron `continuity=true` + monitor-mode skipping the LLM when nothing changed. ✅ [changelog] These are ahead of both peers on paper, but for us they are **study-grade** for O6 and O4, not priority adopts. The community fork with **CaMeL trust boundaries** (`nativ3ai/hermes-agent-camel`, 194★) is the single most relevant artifact to watch for our prompt-injection spine (O4.7 TTSR). ⚠️
